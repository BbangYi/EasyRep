# 운영 SaaS 전수 조사 — 2026-09-20

운영 사이트 <https://habitatos.kro.kr/>의 총괄 관리자 계정에서 접근 가능한 **로그인·주요 메뉴·관리 하위 화면 14종**을 점검했다. 데스크톱과 모바일 화면, 조회 API, 배포된 프런트엔드 코드, 현재 Pi 실행 상태를 함께 대조했다. **기존 샘플 조회와 웹 연결은 작동한다. 현재 Pi 송신 실행은 확인되지 않았고, 재현 가능한 화면 오류 2건을 발견했다.**

팀원이 이미 SaaS 연결을 구성했다는 설명을 전제로 조사했다. 인증키 누락·잘못된 설정·서버 재구축 필요를 확인한 것은 아니다. 이전 01:38–01:51 KST의 1차 점검을 아래 전수 조사 결과로 보완한다.

## 추가 실통신 시험 — 02:15–02:18 KST

사용자는 현재 Pi에 센서·제어 장치를 연결하지 않았다고 확인했다. 아래 센서값은 모두 예시용 가상 자료이며 실측값이 아니다. 장치가 없는 것은 현재 개발 단계의 조건이고, Pi–SaaS 통신 시험을 막는 조건은 아니다.

이번에는 실제 Pi에서 운영 서버로 직접 HTTP 요청을 보냈다. 결과는 다음과 같다.

| 시험 | 실제 결과 | 의미 |
| --- | --- | --- |
| `GET /v1/edge/health` | 200, `status=ok` | Pi에서 HTTPS 서버까지 도달하고 응답을 받음 |
| 인증 없는 `POST /v1/edge/sync` | 401, `invalid_token` | 실제 수신 경로까지 도달했으나 Pi 인증 단계에서 거절됨 |
| 제공된 웹 계정으로 로그인 후 `/api/session/` | 200 | 이 Pi에서 웹 로그인·조회 성공 |
| 웹 세션을 가진 상태에서 센서값 없는 heartbeat POST | 401, `invalid_token` | 웹 로그인 세션만으로 Pi 송신 인증을 대신할 수 없음 |
| 송신 전·후 `/api/enclosures/` 대조 | PI-001 마지막 수신 시각 동일 | 이번 요청이 정상 heartbeat로 수신 처리되지 않았음을 확인 |

서버 응답은 `A registered Pi bearer token is required`였다. 두 POST 모두 Pi Bearer 인증값을 넣지 않은 시험이므로, **팀원이 가진 기존 키가 틀렸다는 검사 결과가 아니다.** 현재 시험 환경에서 사용할 실제 Pi 키의 위치를 찾지 못했다는 것이 남은 조건이다. 조사한 관련 설정 경로·환경·실행 프로세스에서 발견하지 못했으며, 다른 호스트의 설정까지 없다는 뜻은 아니다.

두 번째 POST는 기존 `Gateway`/`CloudSync` 코드로 만든 요청을 `SyncRequest`로 검증했다. `events=[]`, `telemetry=null`, 장치 관측값도 null이다. 제어 루프나 시뮬레이터를 시작하지 않았고 가상 센서값·장치 명령도 생성하지 않았다. 첫 POST는 기존 heartbeat 예시를 인증 없이 보냈으며 401로 거절되었다.

**확인 완료:** Pi–운영 서버 간 HTTP 통신과 웹 로그인. **아직 미완료:** 등록된 Pi 인증을 사용한 heartbeat 수락·ACK·웹 수신 시각 갱신. 기존 PI-001 인증값 또는 이를 읽는 설정 위치가 확인되면 같은 무장치 시험으로 다음 단계를 검증할 수 있다. 새 키 발급이나 센서 장착을 먼저 요구할 필요는 없다.

증거: [직접 요청 결과](../../var/data/pi-saas-check-2026-09-20/network-check.json), [웹 로그인 후 heartbeat 결과](../../var/data/pi-saas-check-2026-09-20/web-session-heartbeat-check.json), [센서값 없는 검증 요청](../../var/data/pi-saas-check-2026-09-20/heartbeat-no-devices.json). 비밀번호·쿠키는 저장하지 않았다.

## 재현된 오류와 수정 지점

### UI-01 — 데이터가 있어도 그래프의 측정 표시가 사라짐

- 재현: 환경 → 마지막 측정 시점 보기 → 온도 또는 조도.
- 실제 결과: 측정 2건이 수치 표·CSV·API에는 있으나, 그래프에서는 센서 점/선이 보이지 않는다. 축과 명령 점선만 보인다.

- 기대 동작: 동일 좌표의 표본도 최소 하나의 측정점으로 표시하고, 개별 이벤트는 시각 선택/상세에서 구분한다.
- 수정 제안: 선과 별도로 측정점을 표시하거나 동일 좌표로만 구성된 선분을 점으로 처리한다. 서로 다른 이벤트를 서버에서 삭제할 필요는 없다.

## 서버 데이터와 시간의 의미

| 항목 | 확인 값 |
| --- | --- |
| 등록 식별자 | `STORE-001 / PI-001 / CAGE-001` |
| 데이터 출처 | `simulation` |
| 샘플 측정 시각 | **2026-09-18 17:00:00 KST** |
| 서버 이벤트 수신 시각 | **2026-09-19 14:32:32 KST** |
| 마지막 Pi 수신 시각 | **2026-09-19 14:32:33 KST** |
| 최신 조회 결과 | `gateway.status=offline`, `stale=true` |
| 센서값 | T1–T5 각각 24 °C, RH1 65 %, LUX1 100 lux |
| 마지막 보고 출력 | 히터·팬·분무 꺼짐, 조명 켜짐. 모두 오래된 가상 자료 |
| 명령 | 조명 5초 켜기 1개, 최종 applied. publishing/published/applied는 그 명령의 처리 이력 3건 |

서버 조회 시각은 서버가 현재 조회 응답에 표시한 시각이다. 그 시각이 계속 갱신되어도 센서 측정 시각이나 Pi 마지막 수신 시각이 갱신된 것은 아니다. 배포 화면은 일반 데이터 10초·세션 15초 간격의 HTTP polling을 사용한다. 현재 등록의 오프라인 기준은 60초이고 센서의 오래됨 기준은 15초다.

전달용 [sync-request.json](../api/sync-request.json)의 이벤트 5건과 운영 API의 ID·순번·종류가 모두 일치했다. payload도 UTC의 `Z`/`+00:00` 표기와 선택적 acknowledged_at/applied_at의 null 추가를 정규화하면 모두 일치한다. 센서값이 실제 장비에서 지금 생성된 값이라고 해석할 수는 없다. 최초 업로드를 어떤 프로세스가 수행했는지는 이번 조회만으로 알 수 없다.

| --- | --- | --- |
| 1 | telemetry.recorded | ca21c579-c662-53cc-b73a-a55a12ae3b71 |
| 2 | command.updated — publishing | bafefa85-3423-583f-a4a4-4f6de4608438 |
| 3 | command.updated — published | 5621dfdd-209a-5582-8b25-688520bb9f10 |
| 4 | command.updated — applied | 239cde9a-ce57-50b3-bd7f-772f646ae08f |
| 5 | telemetry.recorded | b5e57878-3042-5e3b-8ea4-dcccfeff843c |

조회 결과가 존재하고 API·웹·CSV 사이에 일치함을 확인했다. DB에 직접 접속하여 테이블이나 커밋을 조사한 것은 아니다. 추가 실통신 시험의 POST는 인증 단계에서 401로 거절되어 정상 ACK를 받지 못했다.

## API와 인증 확인

| 경로 | 로그인 상태 | 비로그인 상태 |
| --- | --- | --- |
| `/api/session/` | 200 | 401 |
| `/api/enclosures/` | 200 | 401 |
| `/api/enclosures/{cage}/records/` | 200, 전체/종류/검색 조건 동작 | 401 |
| `/api/enclosures/{cage}/commands/` | 200, 최신 명령 1개 | 401 |
| `/api/enclosures/{cage}/history/` | 200, 현재/과거·기간 조건 동작 | 401 |
| `/v1/edge/health` | 200, status=ok | 200, status=ok |
| `/v1/edge/sync` GET | 이번에는 로그인 GET 재검사 생략 | 405, POST용 경로의 정상 메서드 구분 |

비로그인 `/`, `/manage/`, `/manage/site/`, `/profile/`는 302로 로그인 화면에 이동했다. `/login/`은 200이었다. 이 검사는 익명 접근 제한을 확인한 것이며, 총괄 관리자·매장 관리자·사용자 사이의 모든 권한 격리를 검증하지는 않았다.

계약상 필수 경로는 health와 sync다. 웹 조회 API의 구조는 팀원이 만든 운영 구현이다. GET health 성공이나 sync GET 405를 새 데이터 저장·ACK 성공으로 표현하지 않는다.

## 현재 Pi의 실행 상태

같은 작업 공간이 있는 장비는 **Raspberry Pi 5 Model B Rev 1.1, aarch64**다. 02:00 KST 읽기 전용 점검에서 다음을 확인했다.

- `/proc` 조사에서 Gateway·Compute worker·Uvicorn 등 관련 앱 실행을 발견하지 못했다.
- `habitat*` 시스템/사용자 systemd 실행 유닛 및 시스템에 설치된 해당 유닛 파일이 0건이었다.
- `/etc/habitat-gateway`, `/etc/habitatos`, `/opt/habitat-gateway`, `/var/lib/habitat-gateway`가 없었다.
- 조사한 Desktop·사용자 `.config`·예상 실행 경로에서 Gateway SQLite를 발견하지 못했다.
- 저장소의 설정은 예시이며, 과거 송신에 사용한 실제 설정이라고 단정하지 않았다.

따라서 현재 이 Pi에서 계속 송신 중이라는 증거는 없다. 조사 범위 밖의 별도 송신기·다른 장치까지 없다는 뜻은 아니다. SaaS 등록 및 기존 수신 기록과 함께 보면 **기존 연결을 유지하면서 Pi 송신기의 실행 위치·실행 방법·최근 로그를 확인하는 것이 다음 연결 점검**이다. 인증키 재발급이나 설정 재적용을 먼저 요구할 근거는 없다.

게이트웨이의 last_success_at은 메모리 상태이고 ACK를 받은 전송 대기 항목은 삭제되는 구현이다. 조사 범위에서 실행 중인 앱과 실제 DB를 찾지 못했으므로 로컬 과거 ACK 수신을 복원하지 못했다. 조사 증거는 [gateway-runtime.json](../../var/data/site-audit-2026-09-20/gateway-runtime.json)에 있다.

| 기능 | 조사 결과 |

특히 카메라 문구는 실제 카메라 목록 API에서 받은 결과가 아니다. 이전 점검의 “카메라 미등록”은 **화면에 그렇게 표시된다는 의미**로 정정하며, 물리적 카메라나 다른 시스템에 등록이 없다는 증거로 쓰지 않는다. 이 기능들은 현재 센서 수신 계약에 포함되지 않은 후속 기능이므로, 센서 API 고장과 구분한다.
