# EasyRep

이 폴더에는 실제 API를 사용하는 웹 화면과 초기 데모 화면이 함께 있습니다. 수정할 대상을 먼저 구분하세요.

- `standalone/`: React + TypeScript 웹 화면입니다. 로그인한 사용자의 사육장·센서 데이터를 조회하고 카메라 영상과 IR 제어 API를 연결합니다.
- `server/`: 별도로 실행하는 Django 서버입니다. 로그인·권한 확인, Pi 데이터 수신·저장, 카메라·IR 중계를 담당합니다.
- `app/`: Sites/Vinext 빌드 대상입니다. 아래의 초기 데모 실행 안내는 이 화면에 해당하며, `npm run dev`만으로 Django SaaS가 시작되지는 않습니다.

현재 소스와 운영 사이트에 배포된 버전은 별도로 확인해야 합니다. 소스에 기능이 있다는 것만으로 실제 장치 연결이나 운영 배포가 완료된 것은 아닙니다.

## 먼저 볼 안내

- [웹 소스 검사와 빌드](#검증): 공통 시험과 운영 standalone 빌드를 구분합니다.
- [카메라 재연결 구현](#운영-카메라-재연결): 현재 카메라 재생·복구 동작과 검증 범위입니다.
- [브라우저 API 계약](server/docs/web-api.md): 로그인 세션, 센서 조회, 카메라·IR API를 설명합니다.

이 README에는 Django SaaS의 설치부터 운영 실행까지 이어지는 안내가 아직 없습니다. `server/requirements.txt`, `server/manage.py`, `server/config/settings.py`가 서버의 의존성·실행·설정 파일이며, 아래 데모 명령을 운영 서버 설치 절차로 사용하지 않습니다.

## 과거 UI 개발 기록

아래 데모·화면 설계 설명에는 초기 프로토타입 당시의 기능과 제약이 남아 있습니다. 현재 검사 방법은 **검증**, 현재 카메라 구현은 **운영 카메라 재연결** 절을 기준으로 확인하세요.

## 데모 실행 — Sites/Vinext

Node.js 22.13 이상을 사용합니다.

```sh
npm run install:ci
npm run dev
```

표시된 로컬 주소를 열면 홈 대시보드가 나타납니다. 첫 화면은 전체 사육장 목록 `#home`입니다. 카드에서 `#enclosure/crested-01` 같은 상세 경로로 이동합니다. 환경·제어·기록·관리 경로에도 사육장 ID를 유지합니다. 예: `#environment/leopard-02`. 브라우저 뒤로 가기도 지원합니다.

## 데이터 흐름

```text
선택한 사육장의 센서 정의 + 고정 데모 이력
        │
        ├─ getSamples(데모 상태, 기간, 선택 사육장 센서)
        │       ├─ 그래프 / 시간 탐색
        │       └─ makeCsv → 내려받기
        │
        └─ getReadings(데모 상태, 선택 사육장 센서)
                ├─ summarize → 현재 환경
                └─ 센서 위치 / 개별 실측값
```

- 고정 기준시각: 2026-09-15 14:32:00 KST. 실제 현재시각을 나타내지 않습니다.
- 센서 측정시각과 게이트웨이 수신시각은 별도입니다. 데모에서는 수신이 측정보다 10초 늦습니다.
- 사육장 01 정상: 온도 5개, 습도 1개, 조도 1개. 온도는 24.1–26.2 °C입니다.
- 통신 끊김: 14:02 측정 / 14:02:10 수신값을 유지하고 이후 이력은 `null`입니다. 장치 현재 상태는 미확인입니다.
- 센서 오류: T3의 14:22 이후 값은 `null`이며 현재 온도 요약에서 제외합니다.
- 센서 미등록: 센서와 시계열을 모두 빈 배열로 반환합니다.
- 이력은 5분 간격입니다. 미수신 구간은 `null`을 유지하고 `connectNulls={false}`로 표시합니다.
- CSV는 선택한 환경 항목, 기간과 센서만 내보냅니다. UTF-8 BOM, KST 시각, 데모 표기, 오류·미수신 상태를 포함합니다. 없는 값은 빈 칸입니다.
- 사용자 확인 여부와 문제 복구 여부는 각각 `acknowledged`, `recovered`로 분리합니다.
- 환경 적정 범위는 설정하지 않았습니다. 그래프의 Y축 범위는 표시 범위이며 사육 기준이 아닙니다.

## 다음 수정 시 지켜야 할 경계

1. 센서 정보 변경은 `demo.ts`, 계산 규칙 변경은 `model.ts`에서 먼저 처리합니다. 요약 수치만 별도로 하드코딩하지 않습니다.
2. 실제 API를 붙일 때는 타임스탬프와 `null` 의미를 유지하면서 `getSamples`와 `getReadings`에 공급할 데이터를 교체합니다.
3. 제어의 요청 값, 장치 수락, 실제 적용 결과를 하나의 성공 상태로 합치지 않습니다.
4. 공간 추정과 미래 예측은 실측과 별도 데이터 유형으로 추가합니다. 현재는 결과가 없습니다.
5. 실제 로그인, 제어 명령 전송, 푸시 알림, 설치용 manifest와 service worker는 범위 밖입니다. 현재 비활성 버튼을 실제 동작으로 연결할 때 상태와 실패 처리를 함께 구현해야 합니다.

## 검증

의존성을 설치한 뒤 공통 소스 검사와 변경 대상의 빌드·검사를 구분해서 실행합니다. 운영 프런트엔드 `standalone/`과 별도 Sites/Vinext 화면 `app/`은 빌드 대상이 다릅니다.

공통 소스 검사와 타입 검사:

```sh
npm run test:source
npx tsc --noEmit
```

`test:source`는 빌드 산출물 없이 `accounts`, `forest-motion`, `habitat-model`, `live-data`, `live-query`, `live-route`, `spatial`, `presentation`, `camera-playback`의 테스트 파일 9개를 실행합니다. 계정 범위, 진입 연출, 요약·그래프·CSV, 조회 실패·복구, 경로, 실측 출처·센서 배치·보간, 발표 자료, 카메라 재생 복구를 검사하며 테스트 실패는 명령 실패로 전달됩니다. 테스트 파일을 추가하면 이 명시적 목록에도 해당 검사 범위에 맞게 반영합니다.

운영 standalone UI를 변경한 경우:

```sh
npm run build:static
```

정적 산출물은 `dist-static/`에 생성됩니다. 이 빌드는 아래 Sites/Vinext 산출물 검사의 선행 조건을 충족하지 않습니다.

Sites/Vinext 화면을 변경한 경우에는 해당 빌드를 성공시킨 뒤 산출물을 검사합니다:

```sh
npm run build
npm run test:sites-assets
```

`test:sites-assets`는 기존 `tests/initial-load.test.mjs`를 그대로 실행합니다. `dist/client/_next/static/chunks`와 `dist/client/vinext-client-entry-manifest.json`이 필요하며, 없으면 `ENOENT`로 실패합니다. 검사는 Sites 초기 JavaScript의 정적 의존성에서 차트를 제외했는지와 gzip 합계가 220 kB(220,000바이트) 미만인지 확인합니다. 운영 standalone의 크기 예산이나 실제 로딩 성능을 검증하는 명령은 아닙니다.

`node --test tests/*.test.mjs`는 두 범위를 모두 실행하므로 Sites 빌드 산출물도 필요합니다. 소스 검사 통과나 빌드 성공만으로 운영 배포·브라우저·백엔드·실제 장치·성능 검증이 완료된 것으로 간주하지 않습니다.

UI 검토 기준: 1440px, 390px, 중간 너비에서 메뉴 이동·상태 전환·범례·위치 선택·기간 변경·CSV 동작과 키보드 포커스를 확인합니다.

## 배포

Sites 배포 대상은 `.openai/hosting.json`에 기록되어 있습니다. 이 프로젝트를 수정할 때 기존 사이트를 재사용합니다. 배포 접근 제한은 호스팅 계층에서 제공하며 EasyRep 자체 로그인 기능은 구현하지 않았습니다.

## 로고와 환경 화면 수정

- 확정한 투명 원본 PNG 3종은 `public/brand/`에 있습니다. AI로 재생성한 로고는 사용하지 않습니다.
- `components/habitat/brand-logo.tsx`에서 색상·흑백·아이콘 경로와 원본 비율을 관리합니다. 화면은 무손실 WebP를 사용하고 PNG 원본은 보관합니다. 로고를 바꾸면 WebP도 함께 갱신해야 합니다. 크기·알파·보이는 RGB 픽셀이 원본과 같은지 확인한 뒤 교체합니다.
- `inspectSamples`는 표시 중인 센서와 기간의 유효 실측값만 집계합니다. `closestSampleIndex`는 장치 작동 시점과 가장 가까운 실제 측정시각을 선택합니다.
- 그래프 선택선, 시간 슬라이더, 수치 읽기는 같은 선택 시각을 사용합니다. 기간·항목·센서·데모 상태가 바뀌면 마지막 유효 실측을 기본으로 보여줍니다.
- 환경 상세의 위치 도식과 개별값 목록은 현재 선택한 온도·습도·조도 항목을 따릅니다. 도식은 예시 배치입니다.
- 새 라이브러리나 실제 장치 연결을 추가하지 않았습니다.

## 여러 사육장과 사진·카메라

- `enclosures.ts`의 한 항목을 수정하면 목록·상세·관리의 이름, 위치, 센서값, 사진, 카메라 정보가 함께 바뀝니다. 같은 T1 ID를 사용해도 사육장마다 이력은 별도입니다.
- `states`는 사육장 ID별 데모 상태입니다. 상세에서 바꾼 상태는 전체 홈 요약·필터에도 반영됩니다. 새로고침 시 기본 데모 상태로 돌아옵니다.
- 사육장 01은 정상 수신과 카메라 예시, 02는 센서 오류와 카메라 미설치, 03은 통신 끊김과 카메라 끊김, 04는 센서·사진 미등록 예시입니다.
- 대표 사진 변경은 JPG/PNG/WebP 10MB 이하만 받고 이미지 디코딩 성공 후 적용합니다. 브라우저 메모리의 Object URL만 사용하며 교체·해제·화면 종료 때 정리합니다. 서버 업로드, 영구 저장은 없습니다.
- 대표 사진을 바꿔도 카메라 예시 사진은 바뀌지 않습니다. 두 미디어의 책임과 상태를 분리합니다.
- 카메라 상태는 `demo | offline | not-installed`이며 게이트웨이 수신 상태와 독립적입니다. 예시 정지 사진, 고정 예시 시각만 사용하고 실시간 연결·LIVE 표시·임의 재생은 제공하지 않습니다.
- 실제 영상을 연동할 때는 인증된 영상 제공 계층과 플레이어를 연결하고, 연결 중·연결 실패·마지막 프레임의 상태와 시각을 별도 데이터로 공급해야 합니다. 원시 카메라 비밀번호나 RTSP 주소를 브라우저에 넣지 않습니다.
- 실사진 출처와 라이선스는 화면의 사진 출처 및 `public/enclosures/PHOTO-SOURCES.md`에 명시했습니다. CC BY-SA 사진의 재배포·변형 시 해당 이미지의 라이선스를 유지합니다.
- CSV에는 선택한 사육장 이름을 포함해 서로 다른 사육장의 파일을 구분합니다.

## PC 화면 밀도

- 기준은 1920×1080 화면의 Chrome 90%입니다. 브라우저 도구 영역 약 100px를 제외한 레이아웃 영역을 2133×1089 CSS px로 검사했습니다. 브라우저 배율을 코드에서 강제로 바꾸지 않습니다.
- `app/dashboard-layout.css`가 PC 밀도를 담당합니다. Sites와 Pi가 같은 파일을 사용합니다. `--dashboard-gap`, `--dashboard-padding`, `--dashboard-chart-height`로 주요 간격과 그래프 높이를 조절합니다.
- 너비 1600px 이상: 전체 홈 4열, 사육장 상세는 그래프·사진/카메라·장치/기록 3열, 현재 환경은 가로형 수치 카드로 표시합니다.
- 환경 상세는 항목·센서·기간을 한 줄에 모으고, 장치 작동 기록을 그래프 오른쪽에 놓습니다. 1800px 이상에서는 화면 제목·데모 상태·실측/예정 탭·CSV가 한 상단 행에 배치됩니다.
- 화면을 잘라내거나 내부 스크롤로 내용을 숨기지 않습니다. 정보나 펼친 내용이 늘어나면 자연스럽게 문서가 스크롤됩니다. 모바일에서는 같은 내용이 순서대로 쌓이고 하단 메뉴 여백을 유지합니다.
- 2133×1089 검사: 전체 홈, 사육장 상세, 환경 상세의 정상·센서 오류·통신 끊김·미등록 모두 기본 화면이 세로 스크롤 없이 들어왔습니다. 환경 상세의 마지막 안내/푸터 위치는 정상 약 979px, 경고 상태 약 1055px였습니다.
- 1440px와 390px에서는 가로 넘침이 없음을 확인했습니다. 모바일에서 24시간 전환, T1 선택, 키보드 시간 탐색, CSV 내려받기, 습도 전환도 확인했습니다.

## 숲 테마

- `app/globals.css` 맨 위 `:root`에 배경·카드·메뉴·그래프 색상을 모았습니다. `--background`는 밝은 이끼색 바탕, `--card`는 밝은 카드, `--sidebar`는 짙은 숲색 메뉴입니다.
- 선택 상태는 `--primary`·`--accent`, 그래프 5개 선은 `--chart-1`부터 `--chart-5`까지 사용합니다. 범례와 그래프는 같은 색상 변수를 참조하고 선 패턴으로도 센서를 구분합니다.
- 사이드바는 별도 밝은 글자·포커스 색상을 사용합니다. 로고 원본은 변형 없이 밝은 배경 위에 표시합니다.
- 경고·센서 오류·오래된 데이터의 황갈색 표시는 테마와 분리했습니다. 녹색 화면 자체가 사육 환경의 정상 판정이나 건강 점수를 뜻하지 않습니다.
- 색상 변경은 PC·모바일 공통입니다. 기존 Full-HD 밀도 규칙, 데모 데이터, 카메라 상태 및 모바일 터치 영역은 유지합니다.

## 숲 배경과 작업 패널

- `app/forest-scene.css`는 숲 사진과 밝은 작업 패널을 담당합니다. 색상과 기본 UI 배치는 기존 `globals.css`를 재사용합니다.
- 숲 사진은 바깥 여백과 메뉴 아래 전용 공간에 표시합니다. 메뉴 글자는 짙은 녹색 단색 위에, 대시보드 제목·필터·센서는 하나의 불투명 패널 위에 놓습니다. 같은 숲 파일을 재사용해 별도 이미지 다운로드를 늘리지 않습니다.
- `--workspace-surface`는 작업 패널 바탕, `--workspace-inset`은 바깥 여백, `--navigation-width`는 사이드바 폭입니다. PC 16px, 중간 화면 12px, 모바일 8px 여백을 사용합니다.
- `public/textures/forest-interior.webp`는 내장 이미지 생성 도구로 만든 장식용 숲입니다. 실제 사육장 사진이나 카메라 영상이 아닙니다. 생성 프롬프트는 `public/textures/PROMPTS.txt`에 있습니다.
- 배경 교체는 `--forest-image` 경로, 외곽 사진의 암막은 `--forest-shade`로 조절합니다. 메뉴의 나무껍질과 도마뱀 스프라이트는 제거했습니다. `.sidebar-forest`에서 메뉴 아래 숲의 높이·위치를 조절합니다.
- 센서·그래프·장치 패널과 팝업은 불투명 바탕, 어두운 글자, 기존 경고색을 유지합니다. 모바일은 고정 하단 메뉴와 충분한 본문 하단 여백을 사용합니다.
- 사진 로드 실패 시 짙은 녹색 배경이 남고, 진입 화면은 정해진 시간 안에 닫힙니다.

## 숲·로고 진입 연출

- `components/habitat/forest-motion.tsx`는 자동 진입·다시 재생·건너뛰기 상태를 관리합니다. 첫 접속과 새로고침에서 숲·로고 연출을 자동 실행합니다. 기존 조회 화면 위에 표시하므로 재생해도 사육장·필터·센서 선택은 초기화되지 않습니다.
- `INTRO_DURATION_MS` 기본값은 3,200ms입니다. 같은 값을 CSS 변수로 전달해 자동 종료와 화면 전환 시간을 맞춥니다. 처음 약 2.5초는 숲과 원본 로고를 보여주고, 마지막 약 0.7초에 대시보드가 드러납니다.
- 실제 통신·자료 로딩 진행률을 표시하지 않는 시각적 진입 연출입니다. 대시보드 렌더링과 자료 준비는 연출 뒤에서 동시에 진행합니다. 이미지 때문에 무한 대기하지 않습니다.
- `바로 보기`, Tab 또는 Esc로 즉시 종료합니다. 키보드 탐색을 가두지 않으며 운영체제의 `prefers-reduced-motion` 설정에서는 진입 장면을 생략합니다.
- 상단의 다시 보기 아이콘으로 재생할 수 있습니다. 화면 이동마다 자동 반복하지 않고, 평소 대시보드는 정지 상태를 유지합니다.
- CSS의 `forest-brand-arrive`는 로고 등장, `forest-settle`은 배경의 미세한 이동, `forest-entrance-exit`은 마지막 전환입니다. 진입 연출은 `ForestEntrance` 한 컴포넌트로 분리했습니다.

## 초기 로딩 개선

- 진입 연출은 CSS가 시작한 3.2초 안에 종료합니다. 수화 이후 별도 타이머를 다시 시작하지 않고 실제 애니메이션 종료와 상태를 맞춥니다. JavaScript 준비가 늦어도 CSS 종료 시 오버레이가 숨겨져 본문 클릭을 막지 않습니다.
- `environment-chart.tsx`는 기간·센서·데모 상태가 바뀔 때만 이력과 집계를 계산합니다. 시간 탐색 커서를 움직일 때는 같은 이력 배열과 통계를 재사용합니다.
- `environment-chart-loader.tsx`는 그래프가 필요한 상세 화면에 들어갔을 때 차트 모듈을 읽습니다. 로딩 안내와 실패 시 새로고침 안내를 제공하며 다른 메뉴는 유지합니다.
- 센서 미등록 안내는 `unregistered.tsx`로 분리했습니다. 요약 화면에서 안내를 쓰기 위해 차트 코드 전체를 가져오는 의존성을 없앴습니다.
- `public/brand/*.webp`는 PNG 원본과 동일한 크기·알파·보이는 RGB 값을 보존합니다. 실제 화면에서 쓰는 컬러 로고와 아이콘 합계는 849,325B에서 388,260B로 줄었습니다. 원본 PNG는 삭제하지 않았습니다.
- Sites/Vinext 빌드 후 `npm run test:sites-assets`로 초기 정적 의존성에 차트가 포함되지 않는지와 초기 JavaScript gzip 합계 220 kB 미만을 확인합니다. 이는 Sites 산출물의 파일 크기 검사이며 실제 사용자 회선·비공개 접근 확인 시간을 측정한 값은 아닙니다.

## Raspberry Pi 정적 배포

- `npm run build:static`은 기존 React 컴포넌트를 그대로 사용해 `dist-static/`을 생성합니다. 기존 Sites 빌드와 분리되어 있습니다.
- 시작점은 `standalone/main.tsx`, HTML 메타데이터는 `standalone/index.html`, 빌드 설정은 `vite.standalone.config.ts`입니다. 새 화면을 복제하지 않고 `components/habitat`를 공통으로 수정합니다.
- Pi에는 완성된 정적 파일만 옮깁니다. Node·개발 서버·빌드 도구를 상시 실행하지 않습니다. 실제 센서 API나 카메라 서버는 여전히 미연동입니다.
- Pi 경로는 `/srv/habitatos/releases/<release>`, 적용 링크는 `/srv/habitatos/current`로 사용합니다. 이전 배포 폴더는 보존해 링크를 되돌릴 수 있게 합니다.
- `deploy/pi/habitatos-http.conf`는 인증서 발급 전 HTTP 설정, `habitatos-https.conf`는 인증서 발급 후 HTTPS 및 HTTP 리디렉션 설정입니다. `habitatos-enable-https.sh`는 인증서를 발급하고, 설정 검사 성공 후에만 전환합니다. 실패하면 기존 설정을 복원합니다.
- 외부 80·443 포트는 Nginx가 공유하고 `server_name`으로 사이트를 구분합니다. 기존 BbangYi는 내부 4174 서비스, EasyRep는 별도 정적 배포 폴더를 사용합니다. EasyRep 인증서 발급 전에는 해당 도메인의 TLS 연결을 거절하여 기존 사이트로 잘못 연결되지 않도록 합니다.
- Pi의 기존 비공개 콘솔은 Tailscale이 HTTPS를 처리합니다. `0.0.0.0:443` 바인딩으로 변경하거나 기존 호스트 설정을 덮어쓰지 않습니다.
- 정적 배포물에는 Sites의 계정 접근 제한이 포함되지 않습니다. 공개 배포 시 누구나 볼 수 있는 데모 화면이며, 실데이터 또는 개인 정보를 붙이기 전 별도의 인증·권한을 설계해야 합니다.
- 2026-09-16 점검: Pi 5 / ARM64, 기본 디스크 93GiB·외장 SSD 405GiB 여유, 가용 메모리 약 6.9GiB. 정적 파일 17개 약 3.9MB입니다.
- `habitatos.kro.kr` A 레코드는 `49.170.38.14`로 확인됐습니다. `http://habitatos.kro.kr`에서 HTML·스크립트·차트·로고·숲 이미지의 200 응답 및 SHA-256 일치를 확인했습니다. `.env`는 403, 없는 경로와 `SHA256SUMS`는 404입니다.
- 활성 배포는 `/srv/habitatos/releases/release-20260918-accounts`입니다. 이전 배포 폴더와 이전 버전의 해시 기반 스크립트·스타일을 남겨 기존 탭과 되돌리기를 지원합니다.
- 웹서버가 부팅 시 LAN 주소 할당 전에 시작해 실패한 것을 확인해 복구했습니다. `nginx-retry.conf`를 별도 systemd 설정으로 적용하여 실패 시 5초 뒤 재시도합니다. 기존 사이트의 설정 파일은 변경하지 않았습니다.
- HTTPS 발급은 인증기관의 `kro.kr` 등록 도메인 공통 한도에 걸렸습니다. 응답의 재시도 가능 시각은 2026-09-16 19:45:30 KST입니다. `habitatos-tls-bootstrap.timer`가 19:46에 한 번 재시도합니다. 발급 및 전환 성공은 아직 확인되지 않았으므로 HTTPS 완료로 취급하지 않습니다.
- 재시도 상태는 Pi의 `systemctl status habitatos-tls-bootstrap.service`와 `journalctl -u habitatos-tls-bootstrap.service`에서 확인합니다. 인증기관이 다시 제한하면 서비스가 실패 상태와 이유를 남기며, 현재 HTTP 서비스는 유지됩니다. 인증서 발급에 성공하면 기존 certbot 갱신 체계와 웹서버 재적용 훅을 사용합니다.

## 정보 밀도 정리

- 홈의 요약 수치가 필터를 겸합니다. 같은 필터 버튼을 반복하지 않으며, 검색 결과 제목에서 현재 필터와 개수를 확인합니다.
- 마지막 수신시각은 상단, 개별 측정시각은 센서 수치에 둡니다. 데모 표시, 환경 기준 미설정, 센서 오류와 제외, 오래된 데이터 안내는 유지합니다.
- 그래프 아래 센서 범례에 선택 시각의 측정값을 함께 표시합니다. 범례 선택, 시간 탐색, 기간 전환은 같은 데모 데이터를 사용합니다.
- 기간 통계, 사진 출처, 명령 상태 안내는 기본 HTML 펼치기로 확인합니다. 키보드로 열 수 있으며 별도 라이브러리나 저장 상태를 추가하지 않습니다.
- 등록·제어·카메라의 실제 미연동 상태를 유지하고, 기본 화면의 반복 설명과 장치 모델명은 덜어냈습니다. 모델명은 제어 화면에 남아 있습니다.

정보 밀도 정리 후 타입 검사, 배포 빌드, 네 가지 데모 상태의 서버 렌더링과 숲 진입 회귀 검사를 통과했습니다. 앞서 기록한 90% 화면 치수는 배치 정리 버전에서 측정한 결과이며, 이번 문구 정리에서 브라우저 치수를 새로 측정하지는 않았습니다.

## 관리 카드 규격 정리 (2026-09-18)

- 관리 화면은 1400px 이상에서 같은 크기의 카드 6개를 3열·2행으로 표시합니다. 768~1399px는 2열, 모바일은 1열이며 모바일 카드 높이는 내용에 맞춥니다.
- 높이는 고정 숫자가 아닌 공통 격자 행으로 결정합니다. 글자가 늘어나면 함께 커지고 내용이 잘리지 않습니다. 카드 간격 16px, 제목과 본문 여백을 공통으로 사용합니다.
- 긴 센서 목록과 등록·위치 편집 버튼은 기존 상세 패널 방식으로 분리했습니다. 7개 센서·오류 상태·미등록 상태를 유지하며 실제 수정은 비활성화합니다.
- 브라우저에서 2133×1089는 카드 6개 모두 601×269.6px, 1440px는 모두 약 362×269.6px임을 확인했습니다. 1024px·390px에서도 가로 넘침이 없었습니다. 상세 패널 열기·Esc 닫기·포커스 복귀와 센서 오류·미등록 표시를 확인했습니다.

## 운영 카메라 재연결

`standalone/enclosure-viewer.tsx`는 API의 `view=top`을 천장, `view=front`를 전면으로 표시합니다. 장치 목록의 `fresh` 변경은 재생기를 다시 만들거나 사용자의 일시 정지를 해제하지 않습니다. 일시적인 목록 조회 실패로 재생기가 제거되어도 같은 패널에서 카메라별 정지 의도를 보존합니다.

`standalone/camera-playback.ts`는 카메라마다 하나의 확인 요청과 복구 타이머를 관리합니다. 404·503·시간 초과는 최신 재생목록으로 다시 연결하며, 1·2·4·8초 재시도 뒤에는 30초 간격으로 확인합니다. 초기 재생목록 성공만으로 재시도 횟수를 초기화하지 않고, 실제 프레임 표시가 20초간 이어진 뒤 초기화합니다. 프레임 콜백과 재생 품질 카운터로 진행을 확인하며, 사용자 정지·탐색·숨겨진 탭을 영상 멈춤으로 처리하지 않습니다. 복구는 사라진 영상을 복원하거나 지연된 프레임을 최신 영상으로 표시하지 않습니다.

Hls.js는 뒤쪽 버퍼 6초, 목표 버퍼 8초(최대 12초), 최대 따라잡기 속도 1.25배를 사용합니다. 자동 재생이 거부되면 명시적인 재생 버튼을 표시하며, 401·403은 자동 재시도하지 않습니다. 화면 해제 시 확인 요청·타이머·프레임 콜백과 Hls.js를 정리합니다. Safari의 기본 HLS도 같은 복구 수명주기를 사용하지만 버퍼 크기는 브라우저가 관리합니다.

`npm run test:source`에 실제 복구 모듈의 가상 시계 시험이 포함됩니다. 브라우저·운영 서버·실제 두 카메라의 연결 결과는 별도 검증 대상입니다. 정적 파일을 빌드한 것만으로 운영 사이트에 적용된 것은 아닙니다.

실제 `CameraVideo`와 Hls.js를 Chromium에서 확인하는 선택 시험은 다음과 같이 실행합니다.

```bash
cd web
npm ci
npm run test:camera:browser
```

Node.js 22.13 이상, H.264 인코더가 포함된 `ffmpeg`, Chromium이 필요합니다.
기본 브라우저 경로는 `/usr/bin/chromium`이며, 다른 경로는
`EASYREP_CHROMIUM=/path/to/chromium npm run test:camera:browser`로 지정합니다.
로컬 TCP 포트와 headless 브라우저 실행을 허용하는 환경에서 실행하세요.
시험은 임시 디렉터리의 합성 HLS만 사용하며 실제 Pi·카메라·IR API나 운영 계정에
접속하지 않습니다. 종료 시 합성 영상과 브라우저 프로필을 제거합니다.
실제 디코딩 프레임 진행, 503·404·요청 지연 복구, 다른 카메라의 독립 재생,
사용자 정지 유지, 제한된 재시도와 화면 해제를 확인하도록 구성되어 있습니다.
이 시험의 성공은 운영 SaaS 배포·로그인·실제 카메라 연결 검증을 대신하지 않습니다.
